# Audio-Video 2.0：HTTP + LiveKit 客户端

默认使用 HTTPS API 登录、管理房间/资料/头像，WSS 传输公共聊天，LiveKit WebRTC 传输 H.264 和 Opus。
下面旧版本的 TCP/FRP 说明仅适用于显式选择 `transport=tcp` 的兼容模式。

- 房间号使用服务端返回的完整字符串，例如 `room-a1b2c3d4`，加入房间时直接粘贴。
- 保留现有 H.264/NVENC 编码，通过官方 LiveKit SDK 1.13.0 的预编码源发送；不二次编码。
- 语音与系统声音使用 48 kHz 单声道 PCM 混音，经 LiveKit 编码成 Opus；媒体不再依赖 Speex/TCP。
- 根据 WebRTC 关键帧反馈重置编码器，根据带宽反馈调整编码码率。实际 4K/60 fps 效果仍需设备和网络验收。
- JWT 只保存在内存中；登录密码通过 HTTPS 发送，不再给 HTTP 服务提交旧 TCP 协议的 MD5 字符串。
- API 和信令使用域名的 443；媒体直达服务器，部署侧仍需放行 TCP 7881、UDP 50000–51000。

Windows 构建：

```powershell
.\packaging\build-release-msvc.ps1 -Version 2.0.2
```

脚本会下载并校验固定版本的原生 SDK，编译后将 `livekit.dll`、`livekit_ffi.dll`、
`Qt6WebSockets.dll` 与现有运行库一起打包。只配置 SDK 目录的旧占位适配器已替换为实际实现。

登录超时和左上角延迟指标的解释见 [网络诊断说明](docs/login-network-diagnostics.md)。

联调工程：`tests/webrtc_integration.pro`。它创建两个临时账户，通过实际 HTTP API 验证
登录、资料、头像和双向聊天，并让观看端在共享开始后再加入，检查 H.264 解码及 Opus 收音。
账户和头像需要在测试后清理。该测试不等同于 Windows 摄像头/麦克风/4K 桌面联调。

# Audio-Video

[English](README.md) | 简体中文

Audio-Video 是一款面向小型实时会议的 Windows 桌面客户端。项目基于 Qt，提供房间会议、摄像头与桌面共享、语音、用户资料和轻量级 TCP 转发协议。

## 功能概览

- 创建房间，或通过房间号加入已有房间。
- 注册时可选填昵称和头像，也可以在“设置”中后续修改。
- 在房间内使用摄像头或桌面共享，并可在两者之间切换。
- 使用 H.264 视频编码，优先使用 NVIDIA NVENC，其次尝试 Windows Media Foundation 硬件编码，最后回退到 OpenH264 软件编码。
- 观看端会自动聚焦首个远端视频流；媒体连接断开后会恢复订阅，避免进房后一直没有共享画面。
- 使用 Speex 进行语音传输，并提供连接延迟显示。
- 桌面共享时可勾选“系统声音”，并选择跟随 Windows 默认播放设备或指定活动输出设备；系统声音会与麦克风复用现有语音通道发送。
- 桌面共享可由共享者选择 720p、1080p、1440p、4K，以及 15、30、60 fps；客户端会自动匹配最高 72 Mbps 的 H.264 码率。摄像头采集目标为最高 1920 x 1080、60 fps。实际画质会受到采集源、显卡、CPU、网络和接收端设备的共同影响。

## 运行要求

- Windows 10 或 Windows 11，64 位
- 可访问兼容的 Audio-Video 服务端
- 音视频会议需要授予摄像头和麦克风权限
- NVIDIA 显卡及驱动为可选项。没有 NVENC 时，客户端会自动使用软件 H.264 编码。

## 安装与使用

有发布包时，可任选一种方式使用：

1. 运行 `Audio-Video-Setup-<version>.exe`，按安装向导完成安装。默认按当前用户安装，不需要管理员权限。
2. 或解压 `Audio-Video-Portable-<version>.zip`，运行 `Audio-Video.exe`。便携版中的所有文件和目录需要保持在一起。
3. 启动客户端后注册或登录，再创建房间或输入房间号加入会议。

未签名的构建在 Windows 中可能出现未知发布者提示；在使用商业代码签名证书之前，这是正常现象。

## 服务端配置

客户端读取 `Audio-Video.exe` 同目录下的 `config.ini`：

```ini
[Net]
transport=webrtc
gateway=https://video.onnotify.top
livekit=wss://video.onnotify.top
```

服务部署在其他位置时，先修改该文件中的地址和端口再分发。每位参会者都需要能够与这里配置的主机和端口建立持续的 TCP 连接。

面向公网部署时，请阅读 [deploy/README.md](deploy/README.md)。其中包含 FRP 转发、数据库账号、常驻服务和防火墙的配置方式。当前客户端与公网入口之间使用明文 TCP 协议，应部署在受信网络中，或由部署侧提供传输层保护。

### 服务端兼容性

服务端负责房间和媒体包转发，不对视频重新编码。它需要保持现有的 TCP 外层长度帧、原样转发 H.264 负载，并允许最高 8 MiB 的媒体包，以支持 4K 桌面共享。自定义头像还依赖控制连接上的会话令牌校验，以及协议号 `10016` 至 `10019` 的上传、获取处理。当前桌面共享还会使用协议号 `10023`，在新观看端完成视频注册后请求共享端发送新的 H.264 关键帧。

## 从源码构建

Audio-Video 只保留一个构建目标：64 位 MSVC。仓库已包含编译和打包客户端所需的 OpenCV、Speex 与 FFmpeg 发布依赖；不会提交编译产物和调试符号。

### 本机需要安装的工具链

- Visual Studio 2026 Community 或更高版本，安装“使用 C++ 的桌面开发”工作负载和 MSVC x64 工具集
- Qt 6.11.1 MSVC 2022 64 位，默认目录为 `E:\App\Qt\6.11.1\msvc2022_64`；也可以通过 `-QtRoot` 指定
- 只有生成安装包时才需要 Inno Setup 6

Qt 与 Visual Studio 不放入仓库。其余项目专用原生依赖已经提交在 `third_party`：

- `third_party\vcpkg\installed\x64-windows`：OpenCV、Speex 的发布版头文件、库和运行 DLL
- `third_party\ffmpeg-master-latest-win64-lgpl-shared`：客户端所需的 FFmpeg 头文件、导入库和四个运行 DLL

克隆项目后，在 PowerShell 中执行：

```powershell
.\packaging\build-release-msvc.ps1 -Version 1.1.14
```

通用入口 `build-release.ps1` 会执行同一套 MSVC 构建。构建成功后只会在 `dist\MSVC` 中生成：

- `Audio-Video-MSVC-Setup-1.1.14.exe`
- `Audio-Video-MSVC-Portable-1.1.14.zip`

H.264 编解码的独立冒烟测试工程位于 [tests/h264codec_smoke.pro](tests/h264codec_smoke.pro)。

## 画质说明

客户端会先尝试通过 NVENC 进行 H.264 编码。NVENC 不可用时，会继续尝试 Windows Media Foundation 硬件编码，最后才回退到内置 OpenH264 软件编码。桌面共享会以最新帧覆盖过期待发帧，避免堆积后越来越卡；共享标题栏会每秒显示实际釆集、编码、发送 FPS 和为保持低延迟而丢弃的帧数。当采集、编码或视频通道停滞时，客户端会自动恢复；每次开启共享也会刷新视频通道注册。为确保 H.264 视频兼容，建议房间内所有用户使用较新的客户端版本。

采集参数较高并不代表每次通话都能得到相同的清晰度。桌面画质还会受到共享屏幕的分辨率、源图缩放、本地编码性能、实际可用上行带宽、丢包率和接收端解码能力影响。共享文字内容时，建议关闭占用 GPU 的程序并使用稳定的有线网络。

系统声音使用 Windows WASAPI loopback 从所选播放设备采集，再与麦克风混合为现有 8 kHz 单声道 Speex 语音帧，因此适合会议语音和提示音，不是高保真音乐通道。loopback 获取的是播放设备的系统混音；如果把远端声音播放到同一设备，可能产生回声，建议使用耳机或选择独立输出设备。

## 1.1.14 桌面共享关键帧同步

每次进入房间、开始新的桌面共享或连接恢复时，客户端都会重新建立专用视频连接。媒体认证回复和断开通知会统一回到界面线程处理，并且严格绑定产生它的连接，已废弃连接的延迟回调不会再让新连接失去认证状态。当新的观看端完成视频注册后，配套服务端会向正在共享的客户端发送 `10023` 请求，使其立即生成新的 H.264 IDR 关键帧。桌面 NVENC 编码也会严格受所选传输码率限制，避免超大的恒定质量关键帧堵塞 TCP 发送。使用此版本时必须部署配套的服务端源码。左上角延迟标签可点击，用于显示或隐藏顶部的共享详细状态。

发送端会保留已排队的 H.264 关键帧，直到它真正写入视频通道；后续预测帧仍可替换以降低延迟，
但不能再覆盖新观看端开始解码所必需的画面。桌面共享默认把鼠标指针合成进画面，观看端无需
额外设置或提示即可看到鼠标操作。加入房间的房间号输入框使用黑色数字，确保清楚可见。

## 桌面共享自动恢复与连接保护说明

客户端默认直连 `8.163.3.67:8000`。原域名目前经过 Cloudflare 的 HTTP 代理，
无法转发本项目的原始 TCP 协议；仅在服务端地址变更时修改程序同目录的 `config.ini`。

音视频注册同时兼容两种服务端：旧服务端收到 10013 / 10014 注册请求后直接开始转发，
不会回复确认；新服务端可以额外返回 10021 / 10022。客户端成功写出注册包后立即打开
通道，只有 TCP 断开或可选确认明确拒绝时才会重连。

- 登录总等待时间为 20 秒，超时后恢复登录按钮并提示重试。
- 音视频 TCP 连接中断时自动重连；旧登录令牌的回复不会生效。
- 控制连接重新登录后重新申请加入原房间，房间已不存在时提示加入失败。
- 视频通道恢复后重置编码和解码状态，会议窗口显示连接及画面接收状态。
- 注册、房间和资料包均增加编译期结构校验，避免字段或编译器对齐变化后静默产生客户端、服务端协议不一致。

## 传输安全

当前协议为原始 TCP，尚未接入 TLS。完成证书与服务端配套部署前，请只在可信网络或 VPN 中使用，并在服务器防火墙中仅放行已知客户端 IP。

完成 MSVC 构建后，可运行 `tests/run-network-recovery.ps1` 验证客户端注册和
登录超时流程。测试使用本机监听端口和 Qt 无界面模式，不连接正式服务器；
实际两客户端共享屏幕仍需部署后联调。
